# Chapter 6 · striptags: the exit back to plain text, and what the fragment guarantees

> **Enters as:** `Markup('<p>User: <a href="/user/3"><span class="user">Alice &#34;The &lt;b&gt;Great&lt;/b&gt;&#34;</span></a> said: &lt;script&gt;alert(document.cookie);&lt;/script&gt;</p>')`

Before the page moves, one small thing happens beside it. The scenario's assertion about the footer builds its expected value with `Markup("<footer>&lt;/p&gt; &amp; &lt;script&gt;oops&lt;/script&gt;</footer>")`, and the trace duly records another trip through the constructor at line 92 — no `__html__`, no `encoding`, straight to `str.__new__` ([`__init__.py#L122-L131`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L122-L131)). It is the same unguarded door from chapter 1, used the way it is meant to be used: on a literal the developer typed. The comparison succeeds.

Then the page itself is asked for something it has not been asked for before. Every operation so far has preserved or added escaping. `page.striptags()` undoes it.

## Two loops, in a deliberate order

`striptags` starts by taking a plain copy of the text, `value = str(self)` ([`__init__.py#L206`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L206)), and then runs two passes: comments first, tags second.

The comment pass looks for `<!--`, and for each one it finds, looks for a matching `-->` beyond it and cuts out everything between ([`__init__.py#L211-L217`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L211-L217)). Our page has no comments, so `value.find("<!--")` returns `-1` on the first test and the loop body never executes. The code comment just above explains why the pass exists at all and why it comes first ([`__init__.py#L208-L210`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L208-L210)): given `<!-- comment about <em> -->`, a tag-first pass would stop at the `>` of the inner `<em>` and leave ` -->` behind as visible text. Doing comments first means a comment is removed as a unit, whatever it contains. There is a test that pins exactly this, with a comment containing a tag, a comment containing newlines, and an attribute containing newlines ([`tests/test_markupsafe.py#L77-L89`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/tests/test_markupsafe.py#L77-L89)).

The tag pass is the same shape: find `<`, find the next `>` after it, splice them out, repeat ([`__init__.py#L219-L224`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L219-L224)). On our page it fires six times — `<p>`, `<a href="/user/3">`, `<span class="user">`, `</span>`, `</a>`, `</p>` — and then stops, because nothing else in the text is a literal `<`. The `&lt;script&gt;` in the middle has no angle bracket in it; it is nine characters of entity, invisible to a loop looking for `<`. The escaped payload survives this pass as what it has been all along: text.

What is left is

```
User: Alice &#34;The &lt;b&gt;Great&lt;/b&gt;&#34; said: &lt;script&gt;alert(document.cookie);&lt;/script&gt;
```

and the last transformation before the handover is `" ".join(value.split())` ([`__init__.py#L226-L227`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L226-L227)), which collapses every run of whitespace to a single space and trims the ends. Here there is nothing to collapse — removing `</span></a>` left exactly one space before `said:` — but the step matters when tags sat on their own lines; it was a bug fix in 2.1.5 ([`CHANGES.rst#L72`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/CHANGES.rst#L72)). The trace records that string arriving at `Markup.__new__` at line 95.

Both passes use `str.find` rather than a regular expression. That is not a style choice: the regex version had a pathological-backtracking problem, and it was removed in 2.1.4 ([`CHANGES.rst#L80-L81`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/CHANGES.rst#L80-L81)). With `find`, each pass is linear scans over a shrinking string, so no attacker-supplied input can make `striptags` hang. Correspondingly, when a marker is unterminated — a `<!--` with no `-->`, or a `<` with no `>` — the loop does not guess; it `break`s and leaves the rest of the string exactly as it is ([`__init__.py#L214-L215`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L214-L215), [`#L221-L222`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L221-L222)). Stripping is best effort.

## The type is dropped on purpose

The last line is `return self.__class__(value).unescape()` ([`__init__.py#L228`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L228)) — hence the `Markup.__new__` at trace line 95 and the `Markup.unescape` at line 97. `unescape` imports Python's own `html.unescape` lazily and applies it to `str(self)` ([`__init__.py#L195-L197`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L195-L197)), which resolves HTML5 character references. `&#34;` becomes `"`. `&lt;b&gt;` becomes `<b>`. `&lt;script&gt;alert(document.cookie);&lt;/script&gt;` becomes exactly the string the whole run began with.

What comes back, at trace line 99, is

```
User: Alice "The <b>Great</b>" said: <script>alert(document.cookie);</script>
```

and its type is `str`. Not `Markup` — the brief `Markup` wrapper on the line before was only there so that a subclass gets its own `unescape`; the method itself is annotated `-> str` ([`__init__.py#L188`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L188)) and so is `striptags` ([`__init__.py#L199`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L199)). That is the whole warning, and it is an accurate one: the payload is live again, and if this value is printed into a page without being escaped first, the attack the library prevented in chapter 1 happens here instead.

> **For the owner:** `striptags` and `unescape` are the documented exit from the safe world, and they are the two names to grep for in review. They are *not* sanitizers: they strip markers they recognise and give up on ones they don't, and `unescape` is not reversible in the obvious way either — `&amp;lt;` comes back as `&lt;`, and a second `unescape` of the same text keeps decoding ([`tests/test_markupsafe.py#L92-L104`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/tests/test_markupsafe.py#L92-L104)). Their legitimate uses are plain-text summaries, search indexes, email bodies, `<title>` text that will be escaped again on the way out. Any path where their output flows back into HTML without a fresh `escape()` is a finding.

The scenario closes by building its `expected` value with `Markup(...)` over a multi-line literal — the constructor call at trace line 100 — and comparing. The page matches, it is still an instance of `Markup`, and `"<script>" not in page` holds. That last assertion is the point of the whole exercise, and it holds by construction rather than by inspection: no path the comment travelled had any way to put a bare `<` back into the fragment.

## What the fragment actually guarantees

Stated plainly, from what this run showed: anything that passes through `escape` — directly, or via `Markup.format`, `%`, `+`, `join`, `replace`, `ljust`/`rjust`/`center` — has `&`, `>`, `<`, `'` and `"` replaced with entities and comes back typed `Markup` ([`__init__.py#L24-L45`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L24-L45), [`_native.py#L1-L8`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/_native.py#L1-L8)). A value that is already `Markup` fed back through any of those paths is not escaped a second time, because `Markup.__html__` returns `self` ([`__init__.py#L133-L134`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L133-L134)). Whether the C extension or the Python fallback is loaded changes speed, not behaviour: the import prefers `_speedups` and falls back silently ([`__init__.py#L7-L10`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L7-L10)), and the suite is parametrised to run against both ([`tests/conftest.py#L26-L39`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/tests/conftest.py#L26-L39)).

> **For the owner:** The non-guarantees are the half worth writing down. Five characters are escaped and no more — not backtick, not `=`, not whitespace — so safety in an attribute assumes the attribute is quoted; unquoted attributes, `javascript:` URLs, and text inserted inside `<script>` or `<style>` blocks or into JS/CSS string contexts are outside what this library claims. `Markup(text)` blesses anything, and a user-defined `__html__` or `__html_format__` is believed on sight ([`__init__.py#L125-L126`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L125-L126), [`#L340-L349`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L340-L349)), which is why `docs/html.rst` spends its second half on the author's responsibility ([`docs/html.rst#L31-L49`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/docs/html.rst#L31-L49)). Note also that `escape` on such an object calls `__html__` twice — once itself, once inside the constructor — so an implementation with side effects or real cost pays double.

> **For the owner:** Two small things to keep on hand before you sign off. `escape(None)` is `Markup('None')`, a literal four letters in your page; `escape_silent(None)` is `Markup('')` ([`__init__.py#L48-L61`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L48-L61)) — for optional values, the second is nearly always what was meant. And when you need a string rather than markup, `soft_str` converts without flattening an existing `Markup` back to plain `str` ([`__init__.py#L64-L81`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L64-L81)); a bare `str(markup)` discards the type, and the next `escape` will escape it all over again. The three questions worth asking of the codebase that depends on this: where is `Markup()` called on something that is not a literal, what do our `__html__` implementations do with user data, and does anything feed `striptags`/`unescape` output back into a template.

> **Leaves as:** `'User: Alice "The <b>Great</b>" said: <script>alert(document.cookie);</script>'` — a plain `str`, no longer safe and no longer claiming to be — alongside the page, still `Markup`, equal to the expected fragment.
