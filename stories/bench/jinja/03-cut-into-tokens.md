# Chapter 3 · Cut Into Tokens

> **Enters as:** the source `'{% extends "base.html" %}\n{% block t…'` with `name='members.html'`, `filename=None`, arriving at `Environment.compile`

The first thing `compile` does with the string is make a copy of the reference and call it `source_hint` ([environment.py#L758-L762](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/environment.py#L758-L762)). The name is a little flat for what it is: an insurance policy. In a moment the variable `source` will be reassigned — first to a tree, then to generated Python — and if anything downstream raises a `TemplateSyntaxError`, the handler needs the original text to point a finger at the right line. That handler sits around the whole pipeline: parse, generate, compile, all inside one `try` ([environment.py#L759-L770](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/environment.py#L759-L770)).

> **For the owner:** Only `TemplateSyntaxError` is caught here, and it is re-raised through `handle_exception`, which rewrites the traceback so the top frame names the template and line rather than Jinja's internals ([environment.py#L935-L941](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/environment.py#L935-L941)). Any other exception raised during compilation propagates unchanged, so do not rely on this block to contain failures from custom extensions.

Because the source is a `str` and not an already-parsed node tree, it goes to `_parse`, which is one line long: construct a `Parser` and ask it to parse ([environment.py#L617-L621](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/environment.py#L617-L621)). The parser's constructor does not parse anything. It stores the name and filename, and then — before it has looked at a single character itself — it hands the string straight back to the environment to be tokenized ([parser.py#L61-L62](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/parser.py#L61-L62)).

So the string arrives at `_tokenize`, and the first thing that happens to it there is that it is offered to the extensions.

`preprocess` is a `reduce` over `iter_extensions()`, folding the source through each extension's `preprocess` method in priority order ([environment.py#L654-L658](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/environment.py#L654-L658)). This environment loaded no extensions, so the iterator is empty, the fold collapses to `str(source)`, and the trace shows the same string coming back out unaltered. The string has just passed the one place where arbitrary Python could have rewritten it character by character, and nothing was there.

> **For the owner:** Extensions get two hooks on raw template material — `preprocess` on the source text here, and `filter_stream` on the token stream a few lines later ([environment.py#L673-L677](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/environment.py#L673-L677)). Treat adding an extension as adding code to the compile path for every template in the environment.

Next, `_tokenize` asks for a lexer. The `lexer` property does not build one; it calls `get_lexer(self)` ([environment.py#L458-L461](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/environment.py#L458-L461)), which assembles a twelve-element key out of the syntax settings alone — the delimiters, the line prefixes, `trim_blocks`, `lstrip_blocks`, `newline_sequence`, `keep_trailing_newline` — and looks it up in a module-global `LRUCache(50)` ([lexer.py#L428-L449](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/lexer.py#L428-L449), [lexer.py#L22-L24](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/lexer.py#L22-L24)). This is a miss, so a `Lexer` is constructed — seventeen nested calls' worth of `re.escape` and `re.compile`, building the root rule, the block rules, the variable rules, the raw and comment and line-statement rules ([lexer.py#L479-L596](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/lexer.py#L479-L596)) — and cached under that key. Note what is *not* in the key: the loader, the globals, the autoescape setting. Any other environment using stock `{%`/`{{` delimiters will be handed this exact same `Lexer` object.

Now the string is finally cut. `Lexer.tokenize` creates `tokeniter(source, name, filename, state)`, wraps it in `wrap(...)`, and hands that to a `TokenStream` ([lexer.py#L611-L613](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/lexer.py#L611-L613)). Both of those are generators, which means that at this instant the template has still not been scanned. It is about to be scanned one token at a time, on demand, for as long as the parser keeps asking.

Inside `tokeniter`, before the loop starts, the text is rebuilt. `newline_re.split(source)[::2]` chops it into lines on `\r\n`, `\r` or `\n` and throws away the separators; because `keep_trailing_newline` is `False`, the empty final element left by the template's closing `\n` is deleted outright; the lines are then rejoined with plain `"\n"` ([lexer.py#L683-L688](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/lexer.py#L683-L688)). The string the lexer actually works on is one byte shorter than the one the loader produced, and ends at `{% endblock %}`.

> **For the owner:** `keep_trailing_newline` defaults to `False`, so Jinja silently drops one trailing newline from every template ([environment.py#L308](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/environment.py#L308)). For HTML this is invisible; if these templates generate files where a final newline matters, set it to `True`.

`TokenStream.__init__` seeds `current` with a placeholder `Token(1, 'initial', '')` and then immediately calls `next(self)` to pull the first real token ([lexer.py#L331-L337](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/lexer.py#L331-L337)). That pull wakes the generators. The root rule matches the leading `(.*?)` — which is empty, since the template opens with `{%` — and the empty data group is dropped, because `TOKEN_DATA` is in `ignore_if_empty` ([lexer.py#L160-L162](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/lexer.py#L160-L162), [lexer.py#L780-L781](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/lexer.py#L780-L781)). What comes through instead is the opening delimiter, and `wrap` passes it along untouched: `Token(lineno=1, type='block_begin', value='{%')`.

`wrap` is where the raw `(lineno, type, value)` triples become typed values ([lexer.py#L624-L667](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/lexer.py#L624-L667)). Whitespace and comments are discarded; data has its newlines normalised; `'123'` becomes the integer `123`; a quoted string is unescaped through `unicode-escape`, and a failure there is reported as a `TemplateSyntaxError` at the right line rather than a `UnicodeDecodeError`; a name that is not a valid Python identifier is rejected; an operator's text is swapped for its token type. Conversion, classification, validation — and nothing else. No expression is evaluated, no name is looked up, no value from the eventual render is anywhere near this code.

The failures available at this layer are correspondingly narrow. An unbalanced `}` or `)` raises `TemplateSyntaxError('unexpected …')` with the line number ([lexer.py#L798-L812](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/lexer.py#L798-L812)); a character no rule can match raises `unexpected char … at <pos>` ([lexer.py#L866-L868](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/lexer.py#L866-L868)). Both land in the `try` back in `compile` and come out pointing at `members.html`.

Back up the stack: `_tokenize` runs its `filter_stream` loop over the (empty) extension list and returns the stream; `Parser.__init__` walks the same empty list registering custom tags, so `self.extensions` stays `{}` and the parser will only recognise built-in statements ([parser.py#L69-L71](https://github.com/pallets/jinja/blob/5ef70112a1ff19c05324ff889dd30405b1002044/src/jinja2/parser.py#L69-L71)).

The string is now a stream with exactly one token drawn from it and the remaining eight lines still uncut, held in a paused generator. The parser has not yet asked what any of it means — but it is about to, and the question worth holding onto is whether any of this reading has run any of the template's own code. So far, demonstrably, it has not.

> **Leaves as:** a `TokenStream` over `members.html` with `current = Token(lineno=1, type='block_begin', value='{%')`, stored on a freshly built `Parser` whose `extensions` dict is empty
