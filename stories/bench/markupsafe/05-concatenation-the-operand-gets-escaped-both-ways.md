# Chapter 5 · Concatenation: the operand gets escaped, both ways

> **Enters as:** `Markup('<footer>')`, with `'</p> & <script>oops</script>'` waiting on the right of a `+`

The page is finished. What follows in the scenario is a smaller, blunter exercise: building a footer by gluing three pieces together with `+`. It matters out of proportion to its size, because in real application code this is the shape most mixing takes — a safe fragment, a plain string, another safe fragment — and it happens without anyone thinking about escaping at all.

First the literal `'<footer>'` goes through the constructor the story met in chapter 1: `Markup.__new__` with `encoding=None`, which checks for `__html__` (a plain `str` has none), skips the decoding branch, and hands the text straight to `str.__new__` ([`__init__.py#L122-L131`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L122-L131)). No escaping. The developer wrote those angle brackets and means them; the trace returns `Markup('<footer>')`.

Python then evaluates the two `+` operators left to right, so this `Markup` is the left operand of the first one.

## The right operand is escaped, not trusted

`Markup.__add__` is four lines ([`__init__.py#L136-L140`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L136-L140)). It first asks whether the operand is something that can become markup at all: `isinstance(value, str) or hasattr(value, "__html__")`. The payload `'</p> & <script>oops</script>'` is a `str`, so the guard passes. Had it been, say, an `int`, `__add__` would return `NotImplemented` and Python — finding no `int.__radd__` that accepts a `Markup` — would raise `TypeError`. That is deliberate: a `Markup` will not silently stringify arbitrary objects into your document.

The operand is then passed through `self.escape(value)`, the classmethod from the last chapter ([`__init__.py#L230-L240`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L230-L240)), which calls the module-level `escape`. This time the fast path applies — `type(s) is str` is exactly true ([`__init__.py#L39-L40`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L39-L40)) — so `_escape_inner` runs over the characters and the trace shows the constructor receiving `'&lt;/p&gt; &amp; &lt;script&gt;oops&lt;/script&gt;'`.

Look at what happened to the bare ampersand in the middle. In the pure-Python implementation, `&` is replaced *first*, before the four replacements that themselves introduce `&` ([`_native.py#L1-L8`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/_native.py#L1-L8)). Reverse that order and the `&` of every freshly-written `&lt;` would be escaped again into `&amp;lt;`; the whole string would come out double-escaped. The ordering is the entire correctness of that function, and the C version encodes the same thing differently, by writing each replacement directly to an output buffer in one pass ([`_speedups.c#L18-L72`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/_speedups.c#L18-L72)).

With the operand now inert, `__add__` calls `super().__add__(...)` — ordinary string concatenation — and wraps the joined text in `self.__class__`, not in a hard-coded `Markup` ([`__init__.py#L138`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L138)). The trace records the constructor call with `'<footer>&lt;/p&gt; &amp; &lt;script&gt;oops&lt;/script&gt;'` and returns it as a `Markup`. The footer's own tag survived; the payload's did not.

## Safe plus safe is not escaped twice

The second `+` has `Markup('</footer>')` on the right — built, like the first literal, by a plain constructor call at trace line 74. It goes through exactly the same door: the guard passes (a `Markup` is a `str`), and `Markup.escape` is called on it.

Inside, the familiar round trip: `type(s) is str` is false for the subclass, the `__html__` branch is taken, `Markup.__html__` returns `self` ([`__init__.py#L133-L134`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L133-L134)), the constructor calls `__html__` once more on the way in, and `'</footer>'` emerges with its tag intact. Concatenating safe to safe costs an allocation and changes nothing. That idempotence is what lets application code use `+` freely without tracking which side has already been escaped.

The final constructor call yields `Markup('<footer>&lt;/p&gt; &amp; &lt;script&gt;oops&lt;/script&gt;</footer>')`, and `print(repr(...))` runs it through `Markup.__repr__`, which prefixes the class name so the value reads as markup rather than as a string in the output ([`__init__.py#L167-L168`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L167-L168)).

One road not taken here: had the plain string been on the *left* — `"</p> & …" + Markup("<footer>")` — Python would still reach MarkupSafe, because for a subclass operand it tries the reflected method first, and `Markup.__radd__` escapes the left operand before adding ([`__init__.py#L142-L146`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L142-L146)). Direction does not matter; the test for it is one line long ([`tests/test_markupsafe.py#L13-L16`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/tests/test_markupsafe.py#L13-L16)).

> **For the owner:** The `str` API on `Markup` is not uniformly escaping, and the split is worth knowing before you sign off. Methods that *insert* text escape their argument: `join` escapes every element ([`__init__.py#L170-L171`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L170-L171)), `replace` escapes its `new` argument but not `old` ([`__init__.py#L257-L258`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L257-L258)), and `ljust`, `rjust`, `center` escape the fill character ([`__init__.py#L260-L264`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L260-L264), [`#L272-L273`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L272-L273)). Methods that *search* deliberately do not: `strip`/`lstrip`/`rstrip` ([`__init__.py#L266-L276`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L266-L276)), `removeprefix`/`removesuffix` ([`#L297-L301`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L297-L301)) and `partition`/`rpartition` ([`#L303-L311`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L303-L311)) pass their argument through untouched. That was a breaking change in 3.0.0, made so these line up with `in`, `find` and `index`, which never escaped ([`CHANGES.rst#L55-L60`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/CHANGES.rst#L55-L60)). The rule is defensible — you are matching against existing escaped text, not adding to it — but it is a rule a reviewer has to carry in their head, and code written against 2.x may be relying on the old behaviour.

> **For the owner:** The sharper edge is that slicing and splitting return `Markup` pieces without checking what they cut: `__getitem__` ([`__init__.py#L242-L243`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L242-L243)), `split`, `rsplit` and `splitlines` ([`#L173-L186`](https://github.com/pallets/markupsafe/blob/b2e4d9c7687be25695fffbe93a37622302b24fb1/src/markupsafe/__init__.py#L173-L186)) each wrap their results in `self.__class__`. In this footer, `&lt;script&gt;` is 12 characters standing for 8; truncating it for a preview can leave a dangling `&lt;scr`, which is well-typed `Markup` and malformed HTML. It is not an injection — the entity is still inert — but it is output you would not want shipped. If anywhere in the codebase truncates or slices rendered markup, flag it: truncate the plain text *before* escaping, not after.

Everything in this chapter has only added safety: escaped operands, preserved tags, a type that says so. The next step in the scenario asks for the opposite — the plain-text view of the page — and that is the one operation here that gives the entities back.

> **Leaves as:** `Markup('<footer>&lt;/p&gt; &amp; &lt;script&gt;oops&lt;/script&gt;</footer>')`
