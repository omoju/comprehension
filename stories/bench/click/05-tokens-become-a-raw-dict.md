# Chapter 5 · Tokens become a raw dict

> **Enters as:** `args == ['--count=3']` — one string, still exactly as the caller typed it, handed to `_OptionParser.parse_args`

The list arrives at a parser that has never seen it. [`parse_args` wraps it in a `_ParsingState` and then runs two passes over that state: options first, positional arguments second](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L298-L314). The state is four fields and no logic: [`opts` an empty dict, `largs` an empty list, `rargs` the caller's list itself, and `order` an empty list](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L216-L222). `rargs` is the queue of tokens still to read; `largs` is where leftovers accumulate; `opts` is the dict being built; `order` is the record of who was mentioned, and in what sequence.

## One token, classified

[The first pass pops tokens off the front of `rargs` until it is empty](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L328-L341). `'--count=3'` comes off, nine characters long, and gets sorted into one of four buckets. It is not the bare `'--'`, which would [return immediately and leave everything after it unparsed](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L333-L334) — the standard escape hatch for a value that looks like an option. Its first character *is* in `_opt_prefixes` and it is longer than one character, so [it takes the option branch](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L335-L336). The two remaining branches are for non-option tokens: with `allow_interspersed_args` true they go to `largs` and parsing continues; with it false (what a `Group` sets, to hand the rest to a subcommand) the token is [pushed back and the pass stops](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L337-L341).

## Splitting the token

[`_process_opts` looks for an `=` and splits on the first one](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L475-L479): `long_opt = '--count'`, `explicit_value = '3'`. Only the first — a value like `--name=a=b` keeps its own `=` intact. The option half goes through `_normalize_opt`, which is a no-op without a `token_normalize_func`, and comes back as `'--count'`.

Then [the long-option matcher is tried inside a `try`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L484-L500). That `try` is the whole unknown-option policy. If the name is not registered, [`_match_long_opt` raises `NoSuchOption` with the parser's long-option table as the pool of suggestions](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L366-L367), which the exception narrows down [with `difflib.get_close_matches`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/exceptions.py#L254-L260) — that is where `Did you mean '--count'?` comes from. The handler then has three outs: retry the token as a bundle of short options if its prefix is only one character, swallow it into `largs` if `ignore_unknown_options` is set, or re-raise.

Here the name is registered, and the token stays on the road.

## Reclaiming the value

The matched `_Option` is the `store` entry Chapter 4 registered. [`takes_value` is true for `store` and `append`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L165-L167), so the parser does something that reads oddly and is deliberate: [it pushes `'3'` back onto the front of `rargs` and then asks `_get_value_from_state` to consume it](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L370-L378). The comment explains the ordering — the injection happens only in a branch where no exception can follow, so an inserted value is always fully consumed. The alternative branches: an attached value on an option that takes none [raises `BadOptionUsage`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L380-L383), and a flag with no value [gets `UNSET`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L385-L386).

[`_get_value_from_state` sees `nargs == 1` and one token waiting](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L450-L463). It checks whether the next token looks like the start of another option — if it did, and this option were allowed to stand alone, it would return the `FLAG_NEEDS_VALUE` sentinel instead of stealing it. `--count` is not such an option, so the branch is skipped and `'3'` is popped. Had `rargs` been empty, the same two outcomes would apply one level up: the sentinel, or [`BadOptionUsage` saying the option requires an argument](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L437-L449).

[`_Option.process` writes it](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L169-L182): `state.opts['count'] = '3'` under the `store` action, and then, for every action alike, [`state.order.append(self.obj)`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L182) — the Click-level `Option`, not the parser's shadow of it. `order` is now `[<Option count>]`, a record of what the user mentioned and when.

> **For the owner:** The parser performs no type conversion and no validation; `opts['count']` is the string `'3'`, and the declared `default=1`/`INT` type play no part at this layer. Every rule you want enforced on input must be expressed as a parameter type, a `callback`, or a check in your command body — there is no second, hidden validation pass here.

## Nothing left over

The loop finds `rargs` empty and ends. [The second pass asks `_unpack_args` to deal out whatever remains to the declared positional arguments](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L316-L325). This command declares none, so both inputs are empty and [the function returns `((), [])`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L103-L108) — no values to distribute, no unclaimed tokens. `state.largs` is set to `[]` and `rargs` cleared.

One more thing happened invisibly: both passes ran inside [a `try` that catches `UsageError` and only re-raises it when the context is not in resilient-parsing mode](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L308-L314). This run is not resilient, so a parse failure would have escaped normally.

> **For the owner:** `resilient_parsing` discards every `UsageError` raised during parsing and returns whatever was collected so far. Shell completion relies on that, which is why completion still works on a half-typed command line. Do not set `resilient_parsing=True` on a context that will actually execute a command: unknown options and missing values become silent.

> **Leaves as:** `({'count': '3'}, [], [<Option count>])` — the value still a raw string, no leftover tokens, and the user's invocation order recorded for the next stage
