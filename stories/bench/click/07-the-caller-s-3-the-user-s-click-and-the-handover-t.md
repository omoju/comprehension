# Chapter 7 · The caller's '3', the user's 'Click', and the handover to the function

> **Enters as:** `opts={'count': '3'}` with no entry for `--name`, `ctx.params == {}`, and the processing loop now arriving at `<Option count>`

## The token the caller typed

`count` is the only parameter the user actually mentioned, and [the loop reaches it second](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1399-L1400). Its trip through `consume_value` is short: [the parser's dict is consulted first, `opts.get('count', UNSET)` hits, and because the value is not the sentinel the source is `COMMANDLINE`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L2599-L2607). Environment, default map and the parameter's own `default=1` are never consulted — each of those lookups is guarded by `if value is UNSET`, and it is not.

What arrives is still the string `'3'`. The conversion happens one layer up, in [`type_cast_value`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L2634-L2642): `nargs` is 1, so [a single-value converter is built](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L2657-L2660) and the `IntParamType` that chapter 1 inferred from `default=1` is called. [`int('3')` succeeds and the value becomes `3`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/types.py#L598-L610).

Had the caller typed `--count=x`, that same `except ValueError` would have called `fail`, raising `BadParameter`. `augment_usage_errors` would have stamped it with the context and the parameter, and because [`UsageError.exit_code` is `2`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/exceptions.py#L77) the program would have ended with a usage block, a `Try 'hello --help' for help.` hint and `Error: Invalid value for '--count': ...` on stderr. The parser never validates; this is the only place a command-line string is proven to be the type the function expects.

> **For the owner:** Type conversion and validation happen here, between the parser and your function, so a callback body can assume `count` is an `int`. Anything you want enforced — ranges, file existence, mutually exclusive options — belongs in a `ParamType` or a parameter `callback`, not in the function body, because only failures raised here become a clean exit code 2 instead of a traceback.

With `expose_value` left at its default, [the winner of the slot writes the value](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L2909-L2912): `ctx.params` becomes `{'count': 3}`.

## The parameter that has to be asked for

`name` comes last. The dict has nothing for it, no `envvar` was declared and `auto_envvar_prefix` is `None`, there is no default map, and its `default` is still the `UNSET` sentinel — so `Parameter.consume_value` returns `(UNSET, DEFAULT)`. Then [`Option.consume_value` checks the condition that only an option can satisfy](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L3769-L3778): the value is unset, `prompt` is the string `'Your name'`, `prompt_required` is True, and `resilient_parsing` is False. So it prompts.

[`prompt_for_value` computes the default before touching the user](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L3604-L3614) — locking it in before any interaction — and here that default resolves to the sentinel, which [`_hide_unset` presents to `prompt()` as `None`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L3641-L3652), the signal to keep re-asking until something is typed. The important argument in that call is the last one: [`value_proc=lambda x: self.process_value(ctx, x)`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L3650). Whatever the user types is run through the parameter's own type and callback, exactly as a command-line token would be; an answer that fails conversion is rejected and the question is asked again rather than crashing the program.

Under the runner's isolation the prompt never reaches a terminal. `termui.visible_prompt_func` is the [`visible_input` closure installed in chapter 2](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/testing.py#L474-L483): it writes the prompt to the captured stdout, pulls one line from the `BytesIO` holding `'Click\n'`, strips the newline, echoes `Click` back and flushes. That is why [the captured stdout in the trace begins `b'Your name: Click\n'`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/testing.py#L262-L280) before any greeting.

The value comes back as `'Click'` with the source recorded as `PROMPT`, and `ctx.params` becomes `{'count': 3, 'name': 'Click'}`.

> **For the owner:** An option with `prompt=` has no safe non-interactive fallback unless you also give it a `default` or an `envvar`. With stdin exhausted the prompt raises, and [Click's abort handling](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1612-L1624) writes `Aborted!` to stderr and exits non-zero — loud, but a hard failure in any pipeline or CI job that runs this command without a tty. Decide per option whether prompting is a convenience or a requirement, and give the ones that must work unattended a default.

There is a second, quieter consequence of the `value_proc` design: a prompted value is processed twice. `prompt()` runs `process_value` through `value_proc`, and then [`handle_parse_result` runs `process_value` on the returned value again](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L2881-L2883). For a `str` that is harmless. For a parameter callback with a side effect — writing a file, incrementing a counter, calling a service — it fires twice.

## Sweeping up after the loop

With every parameter handled, `parse_args` finishes its own work. First it [walks `ctx.params` and rewrites any surviving `UNSET` to `None`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1411-L1413). Both values here are real, so the sweep changes nothing — but it is the guarantee that the sentinel, useful internally for telling "absent" from "`None`", never reaches user code. Then [the leftover-args check](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1415-L1422): `args` is empty, so nothing fires; had a stray token survived, a plain `Command` (whose `allow_extra_args` is False) would have failed with `Got unexpected extra argument (...)`. Finally [`ctx.args` is set to the empty list and the parser's option prefixes are folded into the context](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1424-L1426).

> **For the owner:** A plain `Command` rejects anything it does not recognise, and that strictness is the default worth keeping. `Group` flips it (`allow_extra_args = True`) so tokens can be handed to a subcommand, and `ignore_unknown_options` turns unknown flags into positional leftovers; both widen what your command will silently accept, so ask what consumes the leftovers before approving either.

## Handing the context back

[`make_context` returns the context](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1386-L1390), and the `scope(cleanup=False)` wrapper unwinds. [`Context.__exit__` drops `_depth` from 2 to 1](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L580-L592) — not zero, so `_close_with_exception_info` is not called and nothing registered during parsing is closed — pops the context off the thread-local stack, and then [`scope`'s `finally` removes the extra depth it added](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L623-L630), leaving `_depth` at 0. A `click.File` argument opened during parsing is still open, as intended.

Immediately [`main` enters the same context with a real `with`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1585-L1588), taking `_depth` to 1 and [pushing it back onto the stack](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/globals.py#L44-L46). This time the matching exit will reach zero, and the teardown is armed. The parameters are converted, the slot dictionary is complete, and the next thing to happen is the call to `hello`.

> **Leaves as:** `ctx.params == {'count': 3, 'name': 'Click'}`, `ctx.args == []`, `parse_args` returned `[]`, and the context re-entered by `main` at `_depth == 1` with `'Your name: Click\n'` already in the captured stdout
