# Chapter 4 · withoutBase stops mangling a false prefix

> **Before:** Input `/admin-dashboard` against base `/admin/` (and again against base `/admin`) started with the string `/admin`, so `withoutBase` sliced off six characters and prepended a slash, handing back the nonsense `/-dashboard` — and the test raised `AssertionError("expected '/-dashboard' to be '/admin-dashboard'")`.
> **After:** The same two inputs come back untouched as `/admin-dashboard`, because the new lookahead sees a `-` where the base ends and decides the base was never really there.

Four cases close out the run, and the first two are where `withoutBase` was actively wrong. The data entering this span is `/admin-dashboard`, carried in alongside a base that `withoutTrailingSlash` has already reduced to `_base = "/admin"` — the same reduction for both the trailing-slash base `/admin/` and the bare `/admin`, which is why the two tests behave as twins.

On both sides the path gets past the first two doors: the base isn't empty, and `input.startsWith("/admin")` is true, since `/admin-dashboard` does begin with those six letters. Before the change, nothing stood between that `startsWith` and the slice. The function [took `input.slice(6)`](https://github.com/unjs/ufo/blob/5fb179d51384301ffb66b48e213863a27cadd1ff/src/utils.ts#L322-L323), which is `-dashboard`, saw its first character was not `/`, and prepended one — producing `/-dashboard` (trace 217, 233). That is the value the base run returned, and against the expected `/admin-dashboard` the test failed both times (trace 215, 231).

After the change, a new step runs between the `startsWith` check and the slice. [`nextChar = input[_base.length]`](https://github.com/unjs/ufo/blob/cb6af4e5e55fc21b5b776fd13b2d1e372f71f40c/src/utils.ts#L326-L327) is `input[6]`, the character sitting right after the matched `/admin` — here the hyphen `-`. [The guard `if (nextChar && nextChar !== "/" && nextChar !== "?") return input`](https://github.com/unjs/ufo/blob/cb6af4e5e55fc21b5b776fd13b2d1e372f71f40c/src/utils.ts#L328-L330) finds that `-` is truthy, is not `/`, and is not `?`, so all three conditions hold and the function returns the input whole: `/admin-dashboard` (trace 219, 235). The slice that mangled it before is never reached. Both tests now pass.

This is the mirror of chapter 2. In `withBase` the lookahead *blocked* an early return so the base could be joined on; here in `withoutBase` the lookahead *adds* an early return so the base is left in place. Same one-character test, opposite consequence, because the two functions want opposite things from a false prefix: one needs to prepend the base, the other needs to not strip it.

The two genuine neighbours in this span confirm the guard only fires on false prefixes. For `/admin/admin-dashboard` minus `/admin/`, `nextChar = input[6]` is `/`, so the guard's `nextChar !== "/"` arm fails, control falls through to the slice, and the result is `/admin-dashboard` on both sides (trace 224–226). For `/admin/dashboard` minus `/admin/`, `nextChar` is again `/`, the slice yields `/dashboard`, and both sides return `/dashboard` (trace 240–242). In each, the character after the base is a real segment boundary, so the old behaviour stands.

> **For the reviewer:** This closes the loop on the earlier question — `withoutBase` receives the same boundary check as `withBase`, with inverted logic, and its false-prefix bug that produced `/-dashboard` is the concrete harm the change removes. The fix is visible fail→pass for exactly these two cases while the genuine-prefix neighbours stay green, so the evidence is clean. The one thing no test here exercises is a `#` fragment boundary, e.g. `/admin#x` against `/admin`; by this code the `#` is a non-boundary char and the input would be returned whole, so confirm with the author that treating `#` as "not having the base" is intended.
