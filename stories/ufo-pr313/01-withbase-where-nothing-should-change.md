# Chapter 1 · withBase, where nothing should change

> **Before:** Ten inputs enter `withBase`; each leaves by one of three doors — empty base, protocol input, or a genuine prefix — and comes out as the trace shows.
> **After:** The same ten inputs leave by the same three doors with the same values, even though a new one-character lookahead now runs on the prefix door.

The first ten test cases hand their data to `withBase(input, base)` and expect to get it back exactly as the base run produced it. These are the untouched cases, and their job here is to prove the new guard doesn't disturb them.

Three of them never reach the changed lines at all. For `"/" + "/"` the base is `/`, so `isEmptyURL(base)` is true and the function returns the input `/` straight away — one unchanged call, output `"/"` (trace 3–6). The same early door catches both protocol inputs: `"/base/" + "https://test.com"` and `"/" + "https://test.com"` return `https://test.com` because `hasProtocol(input)` is true (trace 57–69). On the head this is [the first `if` in `withBase`](https://github.com/unjs/ufo/blob/cb6af4e5e55fc21b5b776fd13b2d1e372f71f40c/src/utils.ts#L291-L293); it reads the same as [the base's](https://github.com/unjs/ufo/blob/5fb179d51384301ffb66b48e213863a27cadd1ff/src/utils.ts#L291-L293), so the data takes the identical path on both sides.

Four more fall past that door to `joinURL`. `"/foo" + ""` turns `""` into `/foo`, `"/foo/" + "/"` gives `/foo`, `"/foo" + "/bar"` gives `/foo/bar` (trace 8–27). In each of these, `input.startsWith(_base)` is false — `""`, `/`, and `/bar` don't begin with `/foo` — so the data skips the prefix branch entirely and lands at [`joinURL(_base, input)`](https://github.com/unjs/ufo/blob/cb6af4e5e55fc21b5b776fd13b2d1e372f71f40c/src/utils.ts#L302). The new lookahead lives inside the prefix branch, so data that never enters that branch never meets it.

The interesting cases are the three that *do* enter the prefix branch and must still come out unchanged. Take `"/base/" + "/base"`: `withoutTrailingSlash` makes `_base` = `/base`, and `input.startsWith("/base")` is true. On the base run, [that was enough to return the input](https://github.com/unjs/ufo/blob/5fb179d51384301ffb66b48e213863a27cadd1ff/src/utils.ts#L295-L297) — output `/base` (trace 33). On the head, the function now reads one character further: `nextChar = input[_base.length]` is `input[5]`, which is `undefined` because the input is only five characters long. [The guard `!nextChar || nextChar === "/" || nextChar === "?"`](https://github.com/unjs/ufo/blob/cb6af4e5e55fc21b5b776fd13b2d1e372f71f40c/src/utils.ts#L296-L300) sees that `!nextChar` is true and still returns the input — same output, `/base`.

The other two prefix cases land on the `/` branch of that same guard. `"/base" + "/base/a"` and `"/base/" + "/base/a"` both reduce `_base` to `/base`, and `input[5]` is `/`; the guard's `nextChar === "/"` arm fires and returns `/base/a` (trace 47, 54). `"/base" + "/base/"` likewise has `input[5]` = `/` and returns `/base/` (trace 41). Every one of these would have returned by the simpler `startsWith`-only check before; now they return by a lookahead that happens to agree with it, because the character after the base is always absent or a `/`.

> **For the reviewer:** These ten cases are your assurance that the guard is a narrowing, not a rewrite. Confirm that for every preserved prefix case the character after the base is `undefined`, `/`, or `?` — the trace shows exactly that, which is why their outputs are identical on both sides.
