# Chapter 8 · `pop` and the Way Out: Teardown That Runs Everything, Even When It Fails

> **Enters as:** `<Response 13 bytes [200 OK]>` back inside `wsgi_app`, with `error = None` and the still-active `<AppContext 4557234128 of scenario, GET 'http://localhost/'>` as `ctx`.

`full_dispatch_request` hands the response back to [`wsgi_app`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L1595-L1619), which does one thing with it: `return response(environ, start_response)`. Calling a Werkzeug response as a WSGI application is what actually starts the HTTP reply — status line and headers go to `start_response`, and the return value is a `ClosingIterator` over the body bytes. But the `return` is inside a `try`, and the `try` has a `finally`. Before that iterator reaches the caller, the finally block runs.

Three things happen there, in order. First, [`if "werkzeug.debug.preserve_context" in environ`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L1609-L1610) — the hook by which the debugger or a `with client:` block asks to keep the context alive past the request. Chapter 2 established that `preserve_context` is `False` here, so the key isn't in the environ and the branch is skipped. Second, a check on [`self.should_ignore_error`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L1612-L1617), which is [`None` on the base class](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/sansio/app.py#L928-L937) and deprecated; nothing to do. Third, [`ctx.pop(error)`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L1619), with `error` still `None`.

## The guards before anything is torn down

[`AppContext.pop`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/ctx.py#L446-L504) refuses to work on the wrong object. It raises `RuntimeError` if this context was never pushed (`_cv_token is None`), if no context is currently active, or — the important one — [if the active context is not `self`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/ctx.py#L465-L479). Mismatched push/pop pairs fail loudly rather than quietly resetting someone else's contextvar. All three checks pass here.

Then [`self._push_count -= 1`, and if it is still positive, `pop` returns immediately](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/ctx.py#L481-L484). This is the mirror of the counting in `push()` from Chapter 4: a context pushed three times (streaming with `stream_with_context`, a preserved test context, a nested re-entry) tears down only when the last pop arrives. Our context was pushed once, the count goes to zero, and teardown proceeds.

## `_CollectErrors`: the reason the rest of this always finishes

The next line is `collect_errors = _CollectErrors()` — trace line 139 — and from here every remaining step is wrapped in `with collect_errors:`. [That context manager's `__exit__` appends any exception to a list and returns `True`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/helpers.py#L665-L674), which suppresses it. The trace is full of these: `__enter__`/`__exit__` pairs at lines 141/161, 163/165, 167/179, 181/183, each returning `True`.

The guarantee this buys is concrete. A teardown function that raises does not prevent the next teardown function from running, does not prevent `request.close()` from releasing uploaded file handles, and — most importantly — does not prevent `_cv_app.reset()`. A buggy teardown callback cannot leave a stale context pinned to the worker for every subsequent request it handles. At the end, [`raise_any`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/helpers.py#L676-L682) re-raises what was collected: a `BaseExceptionGroup` on Python 3.11+, or the first error on older versions. Here the list is empty and `raise_any("Errors during context teardown")` returns `None` (trace line 185).

## The fixed order

[Because `self._request is not None`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/ctx.py#L488-L496), request teardown comes first. [`do_teardown_request`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L1443-L1454) builds its *own* `_CollectErrors` and walks `chain(ctx.request.blueprints, (None,))` — the same innermost-blueprint-first, app-last ordering as `after_request`, with each scope's functions [in reverse registration order](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L1445-L1449). The context is asked for its request, the request recomputes `blueprints` as `[]` (trace lines 146-153), and `self.teardown_request_funcs` has no `None` key. Nothing runs. Then, inside its own collector, [`request_tearing_down.send(self, _async_wrapper=self.ensure_sync, exc=exc)`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L1451-L1452) fires with `exc=None`. No subscribers. `raise_any("Errors during request teardown")` finds nothing.

Next, [`self._request.close()`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/ctx.py#L492-L493) — trace lines 163-165, an enter/exit pair with no call between them visible, because `close()` on a request with no uploaded files does nothing observable.

Then [`do_teardown_appcontext`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L1473-L1482), trace line 169: same pattern, [`reversed(self.teardown_appcontext_funcs)`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L1475-L1477) (empty), then `appcontext_tearing_down` with `exc=None`, then its own `raise_any("Errors during app teardown")`.

Only now, after both teardown phases, does [`_cv_app.reset(self._cv_token)` run and `_cv_token` go back to `None`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/ctx.py#L498-L499). That ordering is a promise to teardown authors: `current_app`, `g`, `request` and `session` are all still live while your cleanup runs. The last step, [`appcontext_popped.send(...)`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/ctx.py#L501-L502), is deliberately on the far side of that reset — subscribers to *popped* see no active context.

> **For the owner:** Write every `teardown_request` and `teardown_appcontext` function so it cannot raise — wrap fallible work in `try`/`except` and log it. Errors raised there are collected and re-raised as an exception group out of `wsgi_app` *after* the response has already been started, so the client has a 200 and your server has a traceback the application cannot turn into an error page.

> **For the owner:** Do not assume a teardown function means the view ran. Teardown is invoked from `ctx.pop()` for every pushed context, including routing failures, `with app.app_context():` blocks in CLI commands and setup code, and preserved test contexts that are popped a second time. Also note the `exc` argument is `None` when an error handler handled the exception, so it is not a reliable "did this request fail" signal.

## The road not taken

Had `hello()` raised, this chapter would look different only in what `exc` carried. [`handle_user_exception`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L885-L898) would search for a handler by status code and MRO across blueprint-then-app scope; finding none for a non-HTTP exception, it re-raises, and `wsgi_app`'s own `except Exception` catches it, records it in `error`, and calls [`handle_exception`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L900-L951). That always sends `got_request_exception`, then reads `PROPAGATE_EXCEPTIONS` — [`None` by default, which resolves to `self.testing or self.debug`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L930-L941), both `False` in this app. So the exception would be logged by [`log_exception`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L953-L967) and the client would get a generic 500 with no traceback — and that 500 would still go through [`finalize_request(..., from_error_handler=True)`](https://github.com/pallets/flask/blob/d73fa1cdcbd8b1465c151db8924ba58b1dd14e35/src/flask/app.py#L943-L951), so after-request hooks and session saving run for error responses too. Then `ctx.pop(error)` would run exactly as above, with the exception passed to every teardown function.

## Out

`pop` returns `None`. The `finally` block ends. The `ClosingIterator` that was built before the finally is returned from `wsgi_app` (trace line 188), from `__call__` (189), and Werkzeug's test machinery iterates it — with the context already gone — into `<WrapperTestResponse streamed [200 OK]>`, which `FlaskClient.open` hands back with `response.json_module` set to the app's provider.

The caller prints `200 OK`, `text/html; charset=utf-8`, and `Hello, World!`.

> **Leaves as:** `<werkzeug.wsgi.ClosingIterator object at 0x10fa1ef90>` yielding `b'Hello, World!'`, surfaced to the scenario as `<WrapperTestResponse streamed [200 OK]>`; the context popped, `_cv_app` reset to no active context, the request closed, and no errors collected.
