# Chapter 3 · main(): the policy at the door, and a context to live in

> **Enters as:** `args=['--count=3']`, `prog_name='hello'`, `standalone_mode=True`

The argument list crosses into Click proper. From here until the function runs, it is in the hands of `Command.main`, which is less a parser than a doorman: it decides where the arguments go, what counts as an answer, and what the process will tell the operating system when it is over.

## Two things that do not happen

`args` was supplied, so the branch that reads `sys.argv[1:]` is skipped entirely, and with it the Windows expansion step: [glob patterns, `~`, and `%VAR%` are only expanded when `args is None` and `os.name == "nt"`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1562-L1568). Our list is simply copied. `prog_name` was supplied too — `'hello'`, from the runner — so [the `_detect_program_name()` fallback](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1570-L1571), which would have looked at `sys.argv[0]` and the `__main__` module to guess whether you ran a file or `python -m something`, never fires.

## The completion door, checked first

Before a single token is parsed, [`main` calls `_main_shell_completion`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1573-L1574). That method derives a variable name from the program name — [dashes and dots become underscores, wrapped as `_{NAME}_COMPLETE`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1665-L1667), here `_HELLO_COMPLETE` — and reads it from the environment. [If it holds anything, Click runs the completion machinery and calls `sys.exit` with its result](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1669-L1677); the program's own logic is never reached. In this run the variable is unset, the function [returns immediately](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1671-L1672), and the trace records that `None`.

> **For the owner:** An environment variable named after the program diverts every invocation into the completion code path and exits before the command runs. Treat `_<PROG>_COMPLETE` as part of the program's input surface in any setting where the environment is not fully under your control, and pass an explicit `complete_var` if you want a name that is harder to guess.

## The policy: every path ends in sys.exit

With completion out of the way, `main` sets up its failure policy before doing any work: [`report = None` and `exit_code = 1`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1576-L1583). The initial `1` matters — anything that produces a message without choosing a code reports failure by default.

The body is a single `try` whose happy path is three lines: [build the context, invoke the command, and call `ctx.exit()`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1585-L1598). The comment there is unusually blunt about why the command's return value is *not* used as the exit code. Below it sits a ladder of handlers, each doing the same two things: re-raise when `standalone_mode` is off, otherwise record a message-writing callable and a code. [`Exit` yields its own code](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1599-L1611); [`Abort` and an interrupted prompt both end in `Aborted!`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1612-L1624); [a `ClickException` contributes `e.show` and `e.exit_code`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1625-L1629); and [an `OSError` is swallowed only when it is `EPIPE`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1630-L1635), by wrapping the streams so the interpreter's final flush cannot raise. Any other `OSError` propagates. Only then does [the message get written and `sys.exit(exit_code)` run](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1637-L1640), with [an outer handler that keeps the chosen exit code even if an interrupt arrives mid-report](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1641-L1645).

> **For the owner:** With the default `standalone_mode=True`, `main` never returns — every path raises `SystemExit`, and the command's return value is discarded rather than used as a status. If you need the return value or want exceptions to propagate to your own handler, call `main(..., standalone_mode=False)` and handle `Exit` and `ClickException` yourself.

## A context to live in

[`make_context('hello', ['--count=3'])`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1355-L1390) first [folds `self.context_settings` into the keyword arguments, but only for keys the caller did not already pass](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1382-L1384) — explicit arguments win over command-level settings. There are none of either here, so `Context` is constructed with the command, `info_name='hello'`, and `parent=None`.

With no parent, every inherited setting falls back to the command's class defaults or to a literal. [`params` and `args` start empty](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L391-L395). [`allow_extra_args` takes `Command.allow_extra_args`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L447-L454), which [for a plain command is `False`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1038-L1045), while `allow_interspersed_args` is `True` and `ignore_unknown_options` is `False`. [`help_option_names` becomes the hard-coded `['--help']`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L478-L485).

One default deserves a second look. [`auto_envvar_prefix` stays `None`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L502-L517) because there is no parent to inherit one from and the caller passed none. That is the switch for *implicit* environment reading: with it unset, no option will quietly take its value from `HELLO_NAME` or `HELLO_COUNT` later. Options with an explicit `envvar=` always read the environment; this prefix is the opt-in for the automatic kind.

Finally the bookkeeping: [empty close-callback list, `_depth = 0`, empty `_parameter_source` and `_param_default_explicit` maps, and a fresh `ExitStack`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L531-L540). That stack is where files opened by a `click.File` parameter, or anything registered with `call_on_close`, will accumulate.

## Entered, but not armed

`make_context` now parses — but first it enters the context in a very particular way: [`with ctx.scope(cleanup=False)`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1388-L1390). `scope` [bumps `_depth` by one before delegating to the context manager and drops it afterwards](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L622-L630), and [`__enter__` bumps it again and pushes the context onto the thread-local stack](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L575-L578). So during parsing `_depth` is `2`, and when the scope closes it will fall to `1` — never to zero, which is the only value at which `__exit__` unwinds the exit stack. The practical effect: resources opened while parsing arguments stay open for the command body.

[`push_context`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/globals.py#L44-L46) puts the context where [`get_current_context()`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/globals.py#L20-L41) can find it — the lookup behind `@pass_context`, behind `echo`'s colour default, and behind any helper that wants to know which command is running. It is thread-local, which is the other half of the runner's single-threaded caveat.

> **For the owner:** Anything a parameter type opens during parsing (a `click.File`, for example) is registered on the context's `ExitStack` and stays open until the outermost `with` block around the context finishes. Register your own resources with `ctx.with_resource` or `ctx.call_on_close` so they are released on the same schedule, including on an early `ctx.exit()`.

The context is live, empty, and on the stack. `parse_args` is the next call.

> **Leaves as:** a `Context` with `params == {}`, `args == []`, `help_option_names == ['--help']`, `allow_extra_args is False`, `auto_envvar_prefix is None`, `resilient_parsing is False`, a fresh `ExitStack`, `_depth == 2`, and `get_current_context()` returning it — about to be handed `['--count=3']`
