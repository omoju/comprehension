# Chapter 4 · Building the parser, and the help option nobody declared

> **Enters as:** the live `Context` (`params == {}`, `help_option_names == ['--help']`) and `args == ['--count=3']`

`Command.parse_args` receives the list first, and its very first line is a question about emptiness: [if `args` is falsy and `no_args_is_help` is set and parsing is not resilient, raise `NoArgsIsHelpError`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1392-L1394). Two of the three are false here — the list has a token in it, and a plain `Command` leaves [`no_args_is_help` at `False`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1072) unless you ask for it — so the list passes through untouched into [`self.make_parser(ctx)`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1396).

## An empty parser that already knows the house rules

[`make_parser` constructs an `_OptionParser` and then asks every parameter to register itself](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1252-L1257). The parser is deliberately thin — the module header says so, and the class docstring adds that it implements nothing that Click handles at a higher level. What it does take from the context are the two switches that change how tokens are grouped: [`allow_interspersed_args` and `ignore_unknown_options` are copied off `ctx`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L256-L258), `True` and `False` respectively for this run. It starts with [empty short- and long-option tables, `_opt_prefixes = {"-", "--"}`, and no positional arguments](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L260-L263).

## The third parameter

`make_parser` iterates over `self.get_params(ctx)`, not `self.params`, and that difference is where a parameter the author never wrote comes into existence. [`get_params` asks for the help option and, if there is one, appends it to a new list](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1128-L1133).

[`get_help_option_names` starts from `ctx.help_option_names` as an ordered `dict`, then walks every user parameter and pops any name it has already claimed](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1212-L1216). `--count` and `--name` claim neither spelling, so the result is `['--help']` — exactly what the trace records. Had the author declared their own `--help`, this list would have come back empty, and [the next check would return `None`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1231-L1234): no automatic option, no error, no warning.

> **For the owner:** Declaring your own option named `--help` (or `-h`, if you set `help_option_names`) silently removes Click's automatic help option rather than colliding with it. If you do that, make your option print the help page itself — `ctx.get_help()` — because nothing else will.

With a name available and `add_help_option` left at its default `True`, [Click imports the `help_option` decorator and applies it to the command](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1240-L1250). The decorator fills in a familiar shape: [`is_flag=True`, `expose_value=False`, `is_eager=True`, help text "Show this message and exit.", and a `show_help` callback](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/decorators.py#L612-L627). Note the second positional declaration Click passes alongside `--help`: `_HELP_OPTION_STORAGE_NAME`, [a reserved string no user parameter is expected to claim](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L59-L61). Because it is a bare identifier, [`_parse_decls` takes it as the explicit storage name](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L3364-L3368) and returns `('_click_default_help', ['--help'], [])`. That indirection is why a user parameter literally named `help` no longer clobbers the help option's slot.

The rest of construction runs the same path Chapter 1 walked: [`_infer_flag_kind(is_flag=True, flag_value=UNSET)`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L3169-L3186) returns `(True, False)`, and [`_pick_type` sees a flag with no `flag_value` and chooses `BoolParamType`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L3211-L3213) — `BOOL` in the trace.

Then a small piece of housekeeping with a real reason behind it. `help_option(...)(self)` appends the new `Option` to `self.params` through `_param_memo`; [`get_help_option` immediately pops it back off and stores it in `self._help_option`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1247-L1250). So `Command.params` is still `[count, name]` afterwards, and every later call returns the same object. The comment above the cache spells out the stake: [callback ordering is computed by object comparison](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1236-L1239), so a fresh help option on each call would break the ordering in Chapter 6. The trace shows the payoff — `get_params` runs twice during parsing, and the second time `get_help_option` returns without rebuilding anything.

## The checks that only exist when you are not optimising

Before returning, `get_params` polices the assembled list. [A `Counter` over every spelling warns about any option used more than once](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1138-L1149). [A second `Counter` over storage names warns in two further cases](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L1151-L1180): a parameter squatting on the reserved help name, and an `Argument` sharing a name with another parameter — which, as the comment notes, silently overwrites a value during parsing. Options sharing a name are left alone on purpose; that is the feature-switch pattern.

Here the counters find nothing: three distinct spellings, three distinct names. The list `[<Option count>, <Option name>, <Option _click_default_help>]` goes back to `make_parser`.

> **For the owner:** All of these duplicate- and reserved-name checks sit inside `if __debug__`, so `python -O` disables them along with the illegal-combination validation in `Option._validate`. They are `UserWarning`s, not errors, even when enabled. Run your test suite without `-O` so a parameter that silently overwrites another's value is reported.

## Three declarations become three parser entries

Each parameter is now asked to describe itself to the parser. [`Option.add_to_parser` picks an action from the declarative settings](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L3422-L3428): `append` for `multiple`, `count` for counters, otherwise `store`. Both `--count` and `--name` are ordinary value options, so both take [the non-flag branch, registering with `nargs=self.nargs`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L3455-L3462) — the trace shows `add_option(obj=<Option count>, opts=['--count'], dest='count', action='store', nargs=1, const=None)`.

The help option takes the other branch: [`store` becomes `store_const`, and since there are no secondary opts, it registers once with `const=self.flag_activation_value`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L3430-L3454). That property is the resolver from Chapter 1 — [an `UNSET` `flag_value` becomes `True` for an actual flag](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/core.py#L3142-L3153) — so the parser stores `True` when `--help` appears, while `Option.flag_value` itself keeps the sentinel for the "did the author pass one?" question.

Inside the parser, [`add_option` normalises each spelling through `_normalize_opt`](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L282-L288) — a no-op here, since [no `token_normalize_func` is set on the context](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L120-L124), so `'--count'` comes back as `'--count'`. [`_Option.__init__` then splits each spelling into prefix and value](https://github.com/pallets/click/blob/06b2a678741131fd577ce170e23e5ca0aeba0309/src/click/parser.py#L141-L154): `_split_opt('--count')` returns `('--', 'count')`, a two-character prefix with a multi-character value, so it goes in `_long_opts` and both `-` and `--` join the prefix set. A declaration whose first character is alphanumeric would have raised `ValueError` right there — options must start with a prefix.

Three calls later the parser holds `--count`, `--name` and `--help` in `_long_opt`, an empty `_short_opt`, and an empty `_args` list, because this command declares no positional arguments.

> **Leaves as:** an `_OptionParser` with `_long_opt == {'--count', '--name', '--help'}` (`--count` and `--name` as `store`/`nargs=1`, `--help` as `store_const`/`const=True`/`dest='_click_default_help'`), `_short_opt` and `_args` empty, `_opt_prefixes == {'-', '--'}`; `Command.params` still `[count, name]` with the help option cached in `Command._help_option`; `args` still `['--count=3']`, unread
