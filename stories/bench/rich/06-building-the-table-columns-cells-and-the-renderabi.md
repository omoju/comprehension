# Chapter 6 · Building the Table: Columns, Cells, and the Renderability Gate

> **Enters as:** `Table(show_header=True, header_style='bold magenta')`, then four column definitions and three rows of plain strings — among them `'[red]Solo[/red]: A Star Wars Story'` and `'[bold]$1,332,539,889[/bold]'`

Nothing is printed in this chapter. Twelve cell strings and four headers arrive, get sorted into columns, and are stored — as they were given, uninterpreted. The interesting work here is what the table *checks* on the way in, and what it decides not to check until much later.

## The container

`Table.__init__` ([`table.py#L188-L250`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L188-L250)) takes two keyword arguments from the caller and about twenty-five defaults from its own signature. The ones that matter later: `box=box.HEAVY_HEAD`, the heavy-topped Unicode frame; `padding=(0, 1)`; `safe_box=None`, which defers to the console; `show_edge=True`; `expand=False`.

Two of those defaults are normalised immediately. `header_style or ""` and `footer_style or ""` turn a `None` into an empty string so later concatenation never has to guard ([`L235-L236`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L235-L236)). And `padding` is handed to `Padding.unpack` ([`L225`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L225)), which expands the CSS-style shorthand: one integer means all four sides, two means (top, right) repeated, four means all four given, and anything else raises `ValueError` naming the length it got ([`padding.py#L60-L74`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/padding.py#L60-L74)). The trace shows the call and its answer: `(0, 1) → (0, 1, 0, 1)`. From here on the table only ever deals in a four-tuple.

The constructor ends with a loop over `*headers` ([`L244-L250`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L244-L250)) that would have turned bare strings into columns. The caller passed none, so it does nothing, and the table exists with `columns == []` and `rows == []`.

## Four columns

`add_column` is called four times ([`L364-L420`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L364-L420)); the trace spells out the first — `header='Date'`, `style='dim'`, `width=12` — and folds the other three. Each call builds one `Column` dataclass and appends it ([`L403-L420`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L403-L420)). Three things are decided there that the caller did not state:

`_index=len(self.columns)` stamps each column with its position at creation time — 0, 1, 2, 3 — and that index is what `_get_padding_width` later uses to know whether a column is the first or last and so whether edge padding applies ([`L700-L714`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L700-L714)). `highlight=highlight if highlight is not None else self.highlight` inherits the table's setting, which is `False` by default ([`L408`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L408)) — so the automatic `ReprHighlighter` that ran over `'Hello'` back in Chapter 2 will *not* run over these cells. And `overflow='ellipsis'` is the signature default ([`L375`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L375)): if a cell turns out wider than its column, the chosen failure is to truncate it with a `…` rather than to break the layout.

`width=12` on the Date column is the only hard constraint in the set; the other three say `width=None`, meaning *measure me*. That distinction is the whole subject of the next chapter.

## Three rows, and the gate

`add_row` runs three times ([`L422-L467`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L422-L467)). The trace shows the first in full: four `is_renderable` checks, each returning `True`, each followed by an `add_cell` into the column at that index.

The list of renderables is first reconciled with the list of columns ([`L446-L450`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L446-L450)): a short row is padded out with `None`, and each `None` becomes an empty-string cell ([`L459-L460`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L459-L460)). A row *longer* than the current columns is not an error either — it grows the table, creating a new `Column` and back-filling every existing row with `Text("")` so the grid stays rectangular ([`L452-L456`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L452-L456)). Here all three rows supply exactly four values, so neither branch is taken.

What each value must pass is `is_renderable` ([`protocol.py#L9-L15`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/protocol.py#L9-L15)): it is a `str`, or it has `__rich__`, or it has `__rich_console__`. Nothing else. An integer, a `datetime`, a `Decimal` — all rejected, with `errors.NotRenderableError` naming the type ([`table.py#L463-L466`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L463-L466)). That is deliberate: `print` will happily pretty-print an arbitrary object, but a table cell will not, because a cell has to be measurable in columns before it can be laid out.

> **For the owner:** `add_row` validates at insert time, not at render time, so a bad cell fails at the line that added it. But the check is interleaved with the mutation: cells for the earlier columns are already appended when a later one raises, and the `Row` is never appended ([`table.py#L451-L467`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L451-L467)). A caught `NotRenderableError` therefore leaves the table ragged — one column holding more cells than `row_count` — and the next `add_row` will misalign. Treat `NotRenderableError` from `add_row` as fatal for that `Table` instance; do not catch it and carry on.

Each accepted value goes into `add_cell`, a three-line closure that appends to `column._cells` ([`L440-L441`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L440-L441)) — the per-column list declared with `field(default_factory=list)` on the `Column` dataclass ([`L114`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L114)). Note the storage shape: cells live on *columns*, not on rows. The `Row` object appended at the end of each call ([`L467`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L467)) holds only a style and an `end_section` flag ([`L131-L139`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L131-L139)); the grid is reassembled by zipping the columns together when it is time to draw.

And the strings are stored exactly as handed over. `'[red]Solo[/red]: A Star Wars Story'` is still thirty-three characters of plain text with square brackets in it. No `markup.render`, no `Text`, no spans. Nothing in this chapter has looked inside a cell.

> **For the owner:** Markup inside cells is deferred, not skipped. It is interpreted later, one cell at a time, when the table is rendered through `Console.render_lines` — which means an unbalanced tag in cell data raises `MarkupError` from inside `console.print(table)`, a long way from the `add_row` that introduced it. If cell content comes from outside your code, convert it at insert time with `Text(value)` (which never parses markup) rather than passing a raw `str`.

> **For the owner:** Row arity is not validated. Too few values are silently filled with blanks, too many silently add a column and back-fill every earlier row ([`table.py#L446-L456`](https://github.com/Textualize/rich/blob/9d8f9a372cc5916fd4781fec207ced7ddac2f08f/rich/table.py#L446-L456)). A loop that occasionally yields a short record will produce a plausible-looking table with the wrong data in it. Assert the length of each row before calling `add_row` if the rows are built programmatically.

> **Leaves as:** a `Table` holding four `Column`s — `_index` 0–3, `width` 12/`None`/`None`/`None`, `justify` left/left/right/right, `highlight` `False`, padding `(0, 1, 0, 1)` — and three `Row`s, with all twelve cells still the original `str` objects
